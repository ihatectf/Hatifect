# Среда разработки и проверки

Прочитай корневые инструкции и `docs/DEVELOPMENT.md`. Python tooling использует stdlib Python 3.11+, тесты — unittest. CI, shell entrypoints и локальная проверка вызывают общую логику. Solution остаётся источником проектной и тестовой матрицы.

Проверки отклоняют неполные доказательства: пустая выборка, ноль тестов, пропуски, несогласованные TRX counters, старый fingerprint или отсутствующий отчёт не дают PASS. Недоступный требуемый tool/runtime — BLOCKED; нарушенный контракт — FAIL. Не обходи ошибку ослаблением test/assertion/acceptance.

При изменении runner проверяй результаты на временных fixtures: выполненные/отклонённые команды, состав пакета, exit/status и evidence. Не фиксируй текст Markdown, случайные номера строк и внутреннюю реализацию тестом ради количества. Обычные команды не устанавливают моды и не запускают игру.

`agent_setup.py` проверяет переносимую конфигурацию без установленного Codex. `--host` отдельно читает реальную конфигурацию и discovered skills через локальный app-server; не создаёт задачи, не вызывает модель, не меняет настройки. Не выводи MCP config, credentials, env или содержимое личных настроек. Доступный skill и применённый skill — разные факты.

После изменения tooling: `./tools/hatifect-test tools`, затем `./tools/hatifect-check`. Для CI проверь workflow синтаксис и фактический run task branch. Изменения Codex сверяй с текущими официальными документами и установленным CLI; неизвестный ключ не считается действующей настройкой. Model, permissions и MCP наследуются от пользователя.
