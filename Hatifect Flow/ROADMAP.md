# Flowline follow-up notes (superseded execution plan)

После уточнения цели 2026-09-06 единственная утверждённая область реализации — [docs/ROADMAP.md](../docs/ROADMAP.md). Этот список сохраняет происхождение исследовательского кода; новые multiplayer/adapters/policies возможности по нему не реализуются. Проверенные части используются только там, где они удовлетворяют требованиям основной roadmap.

Основа одиночных перевозок, управление сетью, целые стопки, возврат, recovery и история реализованы. Production `flow.chest.roundtrip` подтверждён настоящими Saving/Saved/reload. Следующие этапы выполняются последовательно; пользователь разрешил реализацию и связанные проверки без согласований между этапами.

## 1. Multiplayer

- Авторитетный Core/Persistence остаётся только у main host. Farmhand не читает и не пишет SMAPI save data.
- Физические операции используют владельца блокировки инвентаря. Ожидание блокировки сохраняет операцию и custody, не расходует попытку и не отменяет груз.
- Сессии/поверхности привязаны к экрану; события split-screen не закрывают и не ускоряют host owner.
- Клиенты получают ограниченные снимки и отправляют типизированные запросы с session/revision. Хост проверяет peer, save/session, порядок и повтор запроса до побочных эффектов. Физические target capabilities разделены по клиентам.
- Проверки: ожидание/reload/отмена, взаимное исключение inventory, поздний grant/dispose, повтор/stale/foreign requests, disconnect/rejoin, сохранение только host. Реальный multiplayer acceptance имеет отдельный результат.

## 2. Дополнительные inventory adapters

Общий host capability boundary и встроенные поддерживаемые хранилища. Поддержка каждого вида требует явных правил идентичности, вместимости, блокировки и save lifecycle; сторонний API остаётся в отдельном адаптере. Проверки сохраняют количество и полные свойства предметов, исключают общие/виртуальные inventories без подходящей модели владения.

## 3. Деление заявок

Выбор количества и несколько посылок одной заявки. Каждый физический фрагмент получает однозначную custody identity; сумма количества сохраняется при отказе, отмене, возврате и reload. Старые целые стопки и сохранения остаются совместимыми. UI показывает состав и общий прогресс заявки.

## 4. Service policies

Различимое детерминированное поведение ServiceClass/DeliveryGuarantee в admission, очереди и резервировании. Приоритет не нарушает ограниченность работы, fairness и сохранность грузов. Policy сохраняется и одинаково восстанавливается после reload; UI и route preview объясняют выбранное поведение.

## 5. Эксплуатация и acceptance

Безопасное освобождение завершённой истории с сохранением необходимой receipt/custody lineage, чтобы лимит retained записей не превращался в пожизненную остановку сейва. Отдельные runtime-сценарии для возврата, recovery и multiplayer; визуальная проверка EN/RU, scale и lifecycle. Полные host-free/platform/package проверки и новый чистый локальный пакет. Непроведённая проверка не получает PASS.
