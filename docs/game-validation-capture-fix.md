## Cause and scope

The original UI aggregate reported an open Terminal and 620 measured render frames, but `all.png` showed only the game room. `CaptureScreenshot` read the back buffer during SMAPI's `Rendered` event. [SMAPI 4.5.2 raises that event inside the instance's `_draw` override](https://github.com/Pathoschild/SMAPI/blob/4.5.2/src/SMAPI/Framework/SGame.cs). Inspection of the installed Stardew 1.6.15 assembly confirms that `Game1.Draw` calls `renderScreenBuffer` afterwards, combining the world target with the separate `uiScreen`. Neither the back buffer nor the current world target is a complete UI frame during that event.

The test-mode Stardew acceptance controller registers one `DrawableGameComponent` on `GameRunner` at the final draw order. GameRunner draws its components after the instances have composed their buffers; capture then reads the completed back buffer. The old manual row reversal is removed because it inverted this completed-frame readback. A still-bound render target fails explicitly. The controller removes and disposes its component on shutdown; it does not change the game's render target or dispose a game-owned texture. `diagnostics/runtime.json` records the composed-back-buffer source and image dimensions. A second `*-ui-layer.png` retains the completed UI texture for comparison with the final window frame.

This changes no public UI/Flow API, package dependency, persistence format or acceptance threshold. Capture occurs after the performance window ends. Actual macOS game screenshots are the verification for this GPU readback path; no synthetic test is added that merely repeats the branch logic.
