# Runtime-тесты из worktree в Codex

Когда задача или выбранный срез roadmap требует runtime-проверки, Codex самостоятельно подготавливает и запускает executor в терминале текущего worktree. Повторное подтверждение запуска канонического harness и изолированной игры не требуется: разрешение закреплено в корневом `AGENTS.md`. Обычная статическая задача не становится runtime-задачей из-за наличия этой возможности.

VS Code не нужен: `serve` напрямую запускает supervisor и его worker. Задача в `.vscode/tasks.json` остаётся необязательным способом ручного запуска того же executor. `doctor` проверяет transport metadata, SMAPI executable и живое состояние `Ready`; наличие редактора и его задач не входит в условия готовности. Сам запуск `serve` ещё не запускает игру — она стартует при поступлении runtime-сценария.

1. Определи физический корень текущего worktree. Проверь `tools/hatifect.env` по примеру, исполняемый `HATIFECT_SMAPI_PATH` и отдельный для этого worktree mutable test root. При отсутствии локального файла используй уже настроенные переменные или проверенную локальную установку; не копируй чужой env целиком и не подставляй обычные Mods/сейвы. Недостающие prerequisite диагностируй отдельно от разрешения на запуск.
2. Выполни `rtk proxy ./tools/hatifect-runtime-executor status` из этого корня. Переиспользуй живой executor с совпадающим repository root. Если он `Running`, дождись окончания текущего запроса в пределах timeout; не создавай второй экземпляр и не прерывай чужой сценарий. Отсутствующий/stale state и занятый lock — разные состояния; не удаляй lock для обхода владельца.
3. Если живого executor нет, открой управляемую долгоживущую терминальную сессию и выполни ровно `rtk proxy ./tools/hatifect-runtime-executor serve` с рабочим каталогом этого worktree. Для shell tool используй PTY (`tty: true`) и сохрани возвращённый session ID для чтения вывода и штатного завершения. Команду запуска передавай отдельно, без `cd &&`, `nohup`, фонового `&`, встроенного env или оболочки вокруг неё; рабочий каталог задавай параметром инструмента. Если клиент поддерживает показ этой терминальной сессии, открой её панель.
4. Дождись `Ready` с ограниченным временем ожидания и повторно проверь `status`. Успешное создание терминала ещё не означает готовность executor. При startup failure прочитай его вывод/состояние и исправь доступную причину; не повторяй бесконечно тот же запуск.
5. Подготовь текущую сборку и выполни нужный `rtk proxy ./tools/hatifect-smoke <scenario>` или `rtk proxy ./tools/hatifect-ui-test <scenario>`. UI runner сам вызывает isolated prepare; smoke требует соответствующей подготовленной среды. Все mutable Mods/config/saves находятся в разрешённом isolated root, результаты — в `artifacts/runtime/` данного worktree. Не подменяй отсутствующий runtime-отчёт историческим результатом другой сборки.
6. После серии тестов штатно заверши только запущенный этой задачей executor через его терминальную сессию, если продолжение работы не требует оставить его активным. Переиспользованный пользовательский executor оставь работающим. Не используй глобальные `killall` или остановку процессов соседнего worktree.

### Разрешение команды в Codex

В [runtime-executor.rules](../.codex/rules/runtime-executor.rules) разрешён только префикс `rtk proxy ./tools/hatifect-runtime-executor serve`. Он позволяет запускать эту команду вне sandbox без отдельного command prompt, когда правило загружено и более строгая policy его не перекрывает. Правило относится к доверенному проекту и его проверенному harness; это не разрешение произвольных `rtk`, shell, Python, Git или runtime-команд. Общие `approval_policy`, sandbox и личные настройки не меняются.

Правила загружаются при старте Codex из активных config layers. Для нового worktree нужна актуальная версия этих файлов и доверие его точному Git-корню; после добавления правила начни новую сессию Codex. Managed `prompt`/`forbidden` имеет приоритет над `allow`, а разрешения ОС действуют отдельно. Если они блокируют запуск, укажи конкретное ограничение и необходимое действие; не используй другой терминал как обход отказа. Это поведение описано в [OpenAI Rules](https://learn.chatgpt.com/docs/agent-configuration/rules).

Проверка локального правила без запуска executor или игры:

```sh
rtk proxy codex execpolicy check --rules .codex/rules/runtime-executor.rules -- rtk proxy ./tools/hatifect-runtime-executor serve
```

Ожидаемый результат — `allow`. Это проверка совпадения команды с данным файлом правил; она не доказывает наличие SMAPI, готовность тестовой среды или отсутствие более строгой managed policy. `./tools/hatifect-agent-check --host` отдельно проверяет загрузку project config и доступность project skill.
