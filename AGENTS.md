# Hatifect engineering

Работай как Principal Software Architect / Framework & Platform Lead системы **Hatifect**. C# namespaces и assemblies — `Hatifect.*`; команды — `hatifect-*`; переменные среды — `HATIFECT_*`.

## Перед изменением

1. Выполни `git status --short --branch`. Определи область задачи и существующие чужие изменения.
2. Прочитай `ARCHITECTURE.md` и `docs/DEVELOPMENT.md`. Найди owning layer, затронутые контракты, consumer и риски миграции до выбора реализации.
3. Используй `.agents/skills/hatifect-development/SKILL.md` и его `routing.json`. Выбери минимальный набор релевантных skills, полностью прочитай их и сообщи о выборе. Обнаруженный skill ещё не означает использованный.
4. Явно прочитай инструкции затронутых областей: `Hatifect UI/AGENTS.md`, `Hatifect Flow/AGENTS.md`, `Integrations/AGENTS.md`, `tools/AGENTS.md`. При работе из корня они не все загружаются автоматически. Затем исследуй локальные исходники и поведенческие тесты.
5. Перед планированием прочитай [docs/ROADMAP.md](docs/ROADMAP.md). Для работы по roadmap укажи выбранный ID и сверь его статус и зависимости с текущим кодом, Git и evidence; выбирай готовый срез в пределах запроса пользователя. При завершении среза обнови в roadmap статус, результат, ссылки на commit/PR и проверки, ограничения и следующий готовый шаг. Ставь DONE только при подтверждённом выполнении. Для задач вне roadmap сохраняй область запроса без искусственного ID.

Явная авторизация пользователя имеет приоритет над локальными правилами. Не спрашивай повторно уже разрешённое; продолжай обычную обратимую работу. При необходимости продуктового решения сначала подготовь конкретные варианты и доказательства.

## Границы

- Исправляй причину в framework или общем subsystem перед частным consumer.
- Flow Core/Persistence не зависят от UI, Stardew, SMAPI и конкретных сторонних модов.
- Сторонние API изолируются адаптерами; CA использует точные UI packages.
- Consumer задаёт семантику и поведение. Layout, visual policy и отрисовка принадлежат UI framework.
- Публичные API, совместимость persistence, значительные зависимости и acceptance criteria меняются только при явной авторизации задачи.
- Для update/draw/layout/dispatch проверяй allocations, повторные обходы, invalidation и ограниченность коллекций.

## Работа с Git

Один сквозной PR включает контракт, owning implementation и affected consumer. Постоянные отдельные ветки подсистем не нужны. Общий контракт имеет одного ответственного за интеграцию; другие пользовательские задачи работают в отдельных worktree.

Связанные шаги выполняй самостоятельно. В нетривиальной сквозной задаче допускается ограниченное независимое исследование через `hatifect_explorer` или проверка готового diff через `hatifect_reviewer`, если основной агент одновременно может продвигать другую полезную работу. Задание содержит область, вопрос и ожидаемое доказательство. Не делегируй простую правку и не запускай цепочки агентов. Reviewer не исправляет код. Его `read-only` профиль задаёт режим роли; фактические ограничения определяет активная среда Codex.

В начале выполни `git status --short --branch`. `develop` — общая интеграционная ветка. Используй короткую task branch или отдельный worktree. Чужие незакоммиченные изменения сохраняй. Не выполняй reset/clean/stash и не включай чужие изменения в commit. Перед staging и commit проверь полный diff и staged diff.

Прямой push в `develop`, merge, удаление общих веток, force-push, переписывание опубликованной истории и релизы требуют явной авторизации. Локальный task branch/commit допустимы в пределах задачи.

## Проверка результата

1. `./tools/hatifect-check` — инструкции/config, архитектура, Python tests, сборка и тесты без игры.
2. `./tools/hatifect-check --platform` — если затронут игровой адаптер или полный граф; нужны игровые references.
3. `./tools/hatifect-isolated-ui-ca` — при изменении UI package boundary или CA consumer.
4. При исправлениях используй подходящий `./tools/hatifect-test <scope>`; не принимай нулевое число выполненных тестов за успех.
5. Выполни второй проход по исходникам, контрактам и итоговому diff.

После изменения Codex/skills дополнительно выполни `./tools/hatifect-agent-check --host` в целевой рабочей копии. Он проверяет реальную загрузку настроек, а переносимая стадия входит в CI. Не меняй личные model, security или MCP settings без относящегося к ним запроса.

Runtime/SMAPI и визуальная проверка нужны, когда это прямо требует задача или release acceptance. В обычной статической задаче их статус `NOT_APPLICABLE`. Если требуемая стадия не может запуститься, укажи `BLOCKED`; если проверка обнаружила нарушение — `FAIL`; только выполненная успешная проверка получает `PASS`.

Если задача или выбранный срез roadmap требует runtime-проверки, самостоятельно запускай `rtk proxy ./tools/hatifect-runtime-executor serve` в долгоживущем терминале текущего worktree и выполняй нужные изолированные сценарии без повторного вопроса о разрешении на запуск executor/игры. Сначала проверь `status`, используй подходящий живой экземпляр и дождись `Ready`; порядок подготовки и владения процессом описан в [docs/RUNTIME.md](docs/RUNTIME.md). Это разрешение относится к каноническому harness и изолированным тестовым данным; ограничения sandbox, managed policy и ОС остаются действующими. При их отказе сообщи точную причину, не обходи её другим способом запуска.

Не удаляй и не ослабляй действующие тесты ради зелёного результата. Не меняй golden assets, реальные сейвы или обычный Mods пользователя. Обычные команды сборки не разворачивают моды. Runtime harness работает только в явно изолированном каталоге.

В отчёте укажи причину, architectural/API impact, конкретные команды и результаты, изменённые тесты и остающиеся непроверенные условия. Независимый reviewer сообщает находки и доказательства отдельно от исправлений implementer.
